# 2026-08-18 · P0-3：/ext 通道 D3' 落地（GO）

## 决策

**D3' GO**：业务 RPC 通道经文档化 `ctx.connection.rpc.handle('/ext', handler, { authority: 'loopback' })` 注册（`packages/capability-core` Host 半骨架，一个 `ext.probe` 探测方法）。栅栏继承是**结构性的**：`/api` 与 `/ext` 的 Host-loopback / `sec-fetch-site` / Origin 三项检查出自上游同一函数 `isTrustedApiRequest`（`api-request-trust.ts`），在信封解码之前执行；POST-only 与 JSON-only 由通道 fetch handler 执行，对外形态与 `/api` 逐字一致（403/403/403/404/415，PM 与评审各自独立复测）。完整证据链与复现命令见 `docs/spike/P0-3-ext通道验证.md`。

**`authority: 'loopback'` 为产品选型**（PM 裁决）：即使未来部署为 `/api` 配 `trustedHosts`（LAN 放行），`/ext` 业务面仍只收 loopback Host——铁律 6 的纵深防御。企业部署若需 LAN 访问 /ext，改注册参数即可。

**退路裁决（PM）**：退路③（`webServer.register` 自复刻栅栏 ≈120 行）**不备代码**，降级为文档 contingency；退路②（`intercept('/api')`）确证死亡（单拦截器座位被官方 Typert 网关占用，二次注册抛错）。

**bc 错误码策略（PM 裁决，待 P3 细化）**：`RpcErrorCode` 是上游闭集，bc 业务错误当前只能从中取（`bad-request` 已用）；未知 endpoint 的拒绝形态是 HTTP 200 + 业务错误分支（闭集无 404 语义码）——接受此形态，P3 设计业务 RPC 错误码映射时统一定夺，盯梢 `RpcErrorDetailsMap` 增删。

**组装形态**：`profiles/bc-agent/cordis.patch.yml` insert 追加 `bc-capability-core` 行（host-only，无 `dsh.client` manifest → client-modules 扫描器记负缓存，`GET /plugins/<pkg>/client.js` 404 是预期证据）；`apps/desktop/src/main.mjs` 前置泛化为 `BC_PLUGINS` 数组（逐插件幂等 build + `dsh plugin add link:`），后续插件接入只加描述符。
