## 二、必须修正的重大问题（P0）

### 2.1 工作区：上游已原生提供完整持久化，方案误判为"需自建"

这是全方案影响面最大的一处事实错误。

方案多处断言上游没有工作区持久层，需自建 `capability-workspace` + `sessionBindings` 表 + `/ext/workspaces` 路由：

- `01-background.md §2.2`"没有的能力"表：工作区行写"无『保存的项目目录列表 + 会话分组』持久层，需自建"
- `04-spec.md §3.2/§4.1/§4.2/§5`：定义了自建 `workspaces`/`sessionBindings` 两个 domain 文档和 `/ext/workspaces`、`/ext/bindings` 两套 API
- `03-architecture.md D7`：`capability-workspace` 用 `host.pickDirectory` + "最少元数据（id/name/path）"自建

**源码事实**：上游已有一整套原生工作区能力，且已挂入默认 web profile：

1. **完整 `workspace.*` RPC 域**（7 个方法）：`list / create / rename / delete / insertBefore / insertSessionBefore / archiveSession`，全部注册进 `RpcMethodMap`（`packages/host/apiproxy/src/api/rpc-map.ts:46-52`，`packages/host/apiproxy/src/api/workspace.ts`）。
2. **持久化 registry** `ctx.workspaceRegistry`（`@deepseek-ai/dsh-workspace`），经 `ctx.storage.domain` 落盘：`workspaceDomainSpec`（name `workspace`、version 2）含 `workspaces` 表（path/title/sessionIds/createdAt/updatedAt）与全局状态（显示顺序 + `archivedSessionIds` + 两阶段写 pending 标记），见 `packages/workspace/workspace/src/spec.ts`、`src/index.ts`。
3. **会话归属是"由 header.cwd 推导 + 校验"的**，不是方案设想的独立绑定表：`sessionIds` 账户在写路径上始终按 `session.header.cwd` 的 realpath 过滤（`src/entity.ts:202-220`、`src/index.ts:138-149`）。
4. **客户端侧服务已就绪**：`ctx.workspaces`（`packages/client/runtime/src/client/workspaces/`）提供 `list/startSession/connectWorkspace/create/pickDirectory/rename/delete/insertBefore/insertSessionBefore/archiveSession` 完整面。
5. **已挂入默认 web 组装**：`@deepseek-ai/dsh-workspace`（`packages/bundle/web-app/cordis.patch.yml:73-74`）与 `@deepseek-ai/dsh-client-ui-workspace`（同文件 219-220）。官方 UI 侧栏已经按工作区归组、新建会话、归档。

**自相矛盾**：`05-references.md §4.1` 自己就列出了 `workspace.*` 作为 RPC 域，与 `01-background.md §2.2` 的"无持久层"结论直接冲突。说明调研材料已看见该域，但背景文档的结论没有吸收它。

**后果**：若照现方案实施，会出现两套工作区事实源（官方 `workspace.*` 与自建 `/ext/workspaces` + `sessionBindings`），官方侧栏和自研侧栏各读各的，归档/重命名/排序语义互相漂移；且 `session.create({ workspaceId })` 已把"建会话 → 绑定工作区目录 → 归属"一步做完，方案 §3.1 设计的"先解析绑定再 create 再写绑定表"流程是多余的三步。

**建议（评审问题）**：
- 是否接受**复用官方工作区域**（`workspace.*` + `ctx.workspaces` + `session.create({ workspaceId })`），自建侧只保留官方没有的增量——"默认工作区"种子（首次启动预建一个目录并 `workspace.create`）、以及多用户预留字段（`ownerId/status`，可另存一个以 `workspaceId` 为键的轻量 KV 表，不改官方表）？
- `04-spec.md §4.1 workspaces` 与 `§4.2 sessionBindings` 两个 domain 文档是否整体删除或改为"官方域 + 扩展元数据"？
- 官方工作区的 `sessionIds` 是**从 cwd 推导的账户**，方案"绑定不可逆"的说法需要对齐为"cwd 不可变 → 归属自然不可变"，是否仍需要自建 `boundAt` 冗余字段？

### 2.2 会话删除/归档：上游 `workspace.archiveSession` 已提供"隐藏 + 保留日志"语义

`04-spec.md §3.1` 与 `§10.4` 把"删除 = UI 隐藏 + 绑定解除 + 日志保留"当作自建设计，并问"是否有官方删除通道需要补充调研"。

源码事实：`workspace.archiveSession`（`packages/host/apiproxy/src/api/workspace.ts:99-108`）正是这个语义——会话从所有归组界面消失、会话日志与账户槽位保留、可恢复位置。它与方案设想的差异只有一点：归档**保留** `sessionIds` 账户槽位（反归档可还原位置），而方案写的是"绑定解除"。

**建议**：会话删除直接映射到 `workspace.archiveSession`，不要自建 `/ext` 隐藏标记。真正"物理删除"上游不提供（append-only 日志不可变，也确实不该提供），若产品坚持要物理删除，才需要单独调研，但目前方案并未要求物理删除。

### 2.3 R11 已由源码解答：`session.create` 同时接受 `workspaceId` 与 `cwd`

R11 被列为"高"风险，P0 spike ④ 定位为"验证 session.create 如何绑定 cwd"。

源码事实：`session.create` 的入参就是 `{ workspaceId?, cwd?, sessionId?, agentPreset? }`，且 `workspaceId`/`cwd` 互斥（`packages/host/apiproxy/src/api/sessions.ts:246-262`、`sessions.schema.ts:101-116`）。传 `workspaceId` 即"以工作区目录为 cwd 并在发布后 attach 到工作区账户"。

**建议**：R11 降级为"对照当前锁定版本确认签名"，P0 spike ④ 从"发现机制"改为"确认机制"，不必保留"退路=自建 cwd 注入"。这直接降低一期不确定性。

### 2.4 无人值守权限接缝（§10.6 / R4）已有明确答案：`approval/policy ∈ {ask, never}`

`04-spec.md §10.6` 把它列为 P4 前置调研项，R4 标"中"。

源码事实：审批策略是**二元**的——`ApprovalPolicy = 'ask' | 'never'`；`'never'` 在交互式分发之前就拒绝；headless/未完整组装时 answerer 解析为 `unavailable` 并 **fail closed**（`packages/interaction/user-approval/README.md:11,62`、`src/index.ts`）。会话级可通过 `approval/policy` 事件覆盖，permission-presets 提供组合预设：默认 `workspace-write`（`workspace-write` + `ask`）与 `danger-full-access`（`danger-full-access` + `never`）（`packages/interaction/permission-presets/README.md:5`）。

**对方案的影响**：cron 无人值守会话的落点很明确——把该会话的 `approval/policy` 钉为 `never`（或选对应 permission preset），审批请求即自动拒绝并在会话日志留下 `approval/asked`→`approval/decided` 记录。但注意：**没有**"只读放行、写操作拒绝"的分级策略，`never` 是拒绝一切需审批的操作。方案 §3.4 写的"拒绝非只读操作"与 `never`（拒绝全部审批门控操作）不完全等价，需要明确选择其一。

**建议**：把 §10.6 从"待调研"改为已确认；`skipConfirm` 的实现 = 会话级 `approval/policy: never`（或对应 preset），并在规格里写明"`never` 会连只读但需审批的操作一并拒绝"这一取舍。

### 2.5 system-prompt 注入接缝成立，但落日志可能已由上游承担

`04-spec.md §6` 与 C6 依赖"上游 system-prompt 接缝"。

源码事实：接缝真实存在——`ctx.systemPrompt.section({name,order,text})` / `.context(...)` / `.variable(...)`，以及 `system-prompt/assemble` waterfall 事件（`packages/core/system-prompt/`、`packages/boot/app-boot/src/index.ts:822-824`）。**并且上游已把 context 贡献写入会话事件**（`source.plugin`，见 `packages/core/agent-loop/tests/loop.spec.ts` 中 `event.data.source.plugin === '@deepseek-ai/dsh-system-prompt'` 的断言）。

**建议**：方案 §6 第 3 点"每次注入写一条 session 事件"可能需要重新评估——若走 `ctx.systemPrompt.context(...)` 注入，落日志是上游自动完成的，手工再写一条会重复。评审应确认：注入改用官方接缝后，C6 是否**自动满足**，从而删掉自建落日志逻辑。

## 三、中等问题（应澄清或修正设计）

### 3.1 双事实源风险

即使决定自建元数据，也必须以官方 `workspaceId` 为键、以官方 `workspace.*` 为唯一写入口，否则自研侧栏与官方侧栏（若任何页面仍复用官方组件）会出现两套工作区列表。方案目前把工作区完全放在 `/ext/*`，与官方域平行，是最坏的双事实源形态。

### 3.2 业务存储建模：应沿用 `defineDomain` 而非 ad-hoc `<entity>:<uuid>` 键

`04-spec.md §4` 的键策略是 `<entity>:<uuid>`、列表查询全量加载内存过滤。上游 workspace 域已经示范了正确的持久化姿势：`defineDomain({name, version, global, tables})` 经 `ctx.storage.domain` 得到带版本、带 schema 校验、带两阶段写的 domain。方案若自建 cron/library/krm 存储，建议沿用同一 `defineDomain` 机制，而不是手写键约定——否则重演上游已解决的"迁移/一致性"问题，也违背 D4 自己声明的"随上游演进"目标。`10.2` 关于"是否第一天就用 node:sqlite"的问题，在"复用官方 domain 机制"前提下基本消解：单用户量级走 `ctx.storage` domain + 内存过滤即可，真到万级再单开 `node:sqlite`，与本方案结论一致，但应把"KV 全量扫描"写成"domain 表全量 + 内存过滤"并给出量级红线。

### 3.3 "库"的附件来源仅图片；产出文件是另一个 deliverables 概念

`F5` 库的"会话附件"索引来源，上游 attachment 目前**只支持图片**（`imageMediaTypeSchema`：png/jpeg/webp/gif，`sessions.schema.ts:273-279`），不是通用文件附件。而"AI 产出文件"在上游是独立的 deliverables 概念（`ui-deliverables`，按 turn 的 produced files），并非都落在工作区目录。方案 F5 用"工作区目录扫描 + 附件索引"两路，需澄清：非图片的上传附件本期是否有（大概率没有）、产出文件的真实落点是否 100% 等于"会话 cwd 下的工作区目录"（工具写文件可写任意 cwd 内路径，但也可写到别处）。

### 3.4 默认工作区：`workspace.create` 不建目录；"未选归入默认"需显式传参

上游 `workspace.create` 要求目录**已存在**（`workspace.ts:48-57`："no mkdir"）。方案"默认工作区首次种子创建，指向 `$DSH_HOME/workspaces/default/`（自动新建该目录）"需先 `mkdir` 再 `workspace.create`。同时，上游**没有**"默认工作区"概念——`session.create` 省略 `workspaceId/cwd` 时用的是"Host cwd"而非任何默认工作区。方案"未选工作区自动归入默认工作区"必须在 `session.create` 处显式传默认工作区的 `workspaceId`（或 `cwd`），这是一个必须写进规格的实现约束，否则快速开始兜底会静默落到错误的 cwd。

### 3.5 技能"启停"依赖发现边界，需写清 disabled 目录必须落在扫描根之外

方案 §3.3"启停（移入同级 `skills-disabled/` 子目录）"。源码扫描格式是**每根仅一层**：`<root>/<name>/SKILL.md` 或 `<root>/<name>.md`，嵌套 `**/SKILL.md` 不发现（`05-references.md §4.7` 已正确记录）。因此只要 `skills-disabled/` 是**扫描根的同级目录**（如 `~/.dsh/skills-disabled/`）而非根内子目录，机制成立；但若误写成 `~/.dsh/skills/skills-disabled/<name>/SKILL.md`，仍会被发现（`<name>`=skills-disabled 那一层仍在根内）。规格应写死 disabled 目录的绝对层级，并说明 `installPath` 元数据在移动后如何保持同步。

### 3.6 `session.export` 是 GET 下载通道（会话日志 ZIP），非 JSON RPC

`05-references.md §4.1` 把 `session.export` 列进 `session.*` RPC 域，实际它是 GET 下载面（`downloads.sessionLog`，导出根会话日志 ZIP + 可选子代理后代），**不进 `IApiClient`**、无 wire 信封（`packages/host/apiproxy/src/api/downloads.ts`）。方案 F1"导出（session.export，后置）"不受影响，但应更正为"会话日志 ZIP 下载"语义，前端调用方式与 `/api` 一元 RPC 不同。

### 3.7 React 版本：`^18.2.0` 而非固定的"18.3"

`apps/web/package.json:30` 是 `"react": "^18.2.0"`（caret，实际解析到 18.3.x）。C5 与 §2.2"官方 client runtime 为 18.3"的方向正确（需降到 18.x 共享运行时），但"18.3"不是锁定的版本号。若要做严格双 React 实例风险控制，应在 P0 验证时以**实际解析版本**（`pnpm ls react` 结果）为准，并考虑在自建包上锁同一 caret 范围。

## 五、对方案自问评审问题的逐条回答

### 5.1（README Q1 / 04-spec §10.1）记忆引擎：自建 vs TAM

**结论：自建成立，不必引入 TAM。** 论据链（sidecar 子进程、`sqlite-vec` alpha + `@node-rs/jieba` 按 Electron ABI 重编译、Node≥22.16、每 5 轮触发 LLM 抽取的持续 token 成本、beta 稳定性、MCP 不暴露记忆能力）与"用户主导四类型管理 UI"哲学不匹配的论证是充分的。补充两点：
1. "第三条路"——借鉴 TAM L1 的 **dedup**（向量相似度去重）作为 P3 后的可选增强，方向对，但单用户量级、手动录入的记忆去重价值有限，可明确为"不做，等自动沉淀功能启动时再评估"。
2. TAM 的 MemoryKnowledge（code-graph/wiki）作为知识库增强走 `mcp-client` 挂载，是 MCP 的正确位置，建议保留为路线图项即可，不进本期范围。

### 5.2（README Q3 / §10.2）业务存储：ctx.storage KV vs 自建 SQLite

**结论：选 `ctx.storage` 正确，但建议用 `defineDomain` 机制建模（见 §3.2），并给出量级红线。** "第一天就用 node:sqlite"的理由（索引/分页/FTS5）在单用户量级不成立；真正会逼出自建库的是"库"的全量文件索引分页与搜索，而 F5 已把库简化为目录扫描 + 元数据，万级以内内存过滤足够。给出一条明确切换线（例如"单一 domain 文档数超过 N 万或查询出现分页倒排需求时，再在插件内开 `node:sqlite` 自有库，不碰上游库"），D4 的"保留升级路径"就闭环了。

### 5.3（README Q2 / §10.3）对话区嵌入深度

**结论：整体嵌入 + CSS 换肤方向正确，但 P0 spike 应追加"官方 conversation 组件树样式审查"这一项。** 风险不在"能否嵌"（slot 系统已保证结构可嵌），而在 manus 风格（300px 侧栏、暖灰、无边框气泡）与官方组件（语义别名 + 工具卡片）的视觉粒度差异。建议 P0 明确产出：① 一份官方 conversation/details 可覆盖与不可覆盖的 CSS 变量清单；② 对"不可覆盖"的硬编码项（如有）给出逐块替换优先级。§10.3 自问的"是否追加样式审查项"——答案是**是**。

### 5.4（§10.4）会话删除语义

**结论：可接受，且直接复用 `workspace.archiveSession`（见 §2.2）。** 唯一需要修正的是"绑定解除"改为"保留账户槽位"，物理删除确认不做（append-only 不可变）。

### 5.5（§10.5）多用户预留策略

**结论：`ownerId/status` 两个零成本字段之外，建议补一个与 v0.8.1 对齐的决策点：部门可见范围（usage_scope）是否需要现在进模型。** 当前 §4.9 明确不保留 usage_scope，理由成立（无 UI、无写入分支）。但这是"日后改不动"的高危项：一旦单用户期有真实数据，事后给 memories/knowledge 加 scope 可见性会面临存量数据回填。建议至少**在 domain 文档里**为 memories/knowledgeEntries 预留一个默认 `scope: global` 的字段（恒为 global，不进 UI），成本为零，避免未来硬迁移。这与 §4.9"不得产生 UI 复杂度或写入分支"不冲突（字段恒默认值）。

### 5.6（§10.6）无人值守权限调研

**结论：已确认，见 §2.4。** 无需再作为 P4 前置调研，直接写规格：`skipConfirm` = 会话级 `approval/policy: never`（或 `danger-full-access` preset），并接受"`never` 拒绝一切需审批操作（含只读）"的语义。

### 5.7（§10.7）其他评审项

1. **双通道维护成本**：`/ext/*` + `/api` 并存本身没错（RpcMethodMap 封闭），但当前把**工作区**也放进了 `/ext`，这是把本可零维护的官方域变成了自维护域。修正后，`/ext/*` 只剩 cron/library/skills-meta/krm 四个真正的新域，维护成本显著下降。全部走自定义 WS 反而更差（丢官方信任栅栏、丢官方 slot/事件复用），不推荐。
2. **P3 过重**：P3 一次放 workspace/skillx/library/krm 四个插件，且在 workspace 复用官方域后，P3 实际只剩 skillx/library/krm 三个 + 大量前端移植。建议仍拆：P3a = krm（注入链 + 落日志，风险最高，独立验收 S4），P3b = library + skillx（目录/文件操作）。cron 保持 P4。
3. **风险清单遗漏项**：
   - **双 React 实例**风险未单列（C5 提到降级，但 R 表没有）。应补 R13：若任何官方组件/自研组件间出现跨运行时互嵌失败，后果与缓解。
   - **Electron 下 `ctx.storage` 默认后端**：web profile 下 `session-query` 默认 `:memory:` + `openAt: never`，桌面若想用 FTS 搜索需 patch 开启且禁指向持久化库；方案未提桌面版搜索是否要开，建议补决策。
   - **官方 UI 插件与本方案禁用 `ui-layout` 的相互作用**：禁用 `ui-layout` 后，官方 `ui-workspace`/`ui-sidebar` 等子 slot 组件仍会注册，需在 P0 验证"禁用 ui-layout + 自占 root"时这些官方子 slot 内容是否/如何复用，避免出现两套侧栏。
4. **Windows-first 与上游 pwsh 沙箱**：上游沙箱在 Windows 下为 PowerShell ConstrainedLanguage（只读）与 FullLanguage（workspace-write），且不能开命名管道捕获子进程 stdio。方案 F4 cron 起会话执行、F5 目录扫描若依赖捕获子进程输出，会撞这条边界。建议把"Windows 沙箱对 cron 触发链路/库扫描的约束"作为 P4/P3 的显式验证项，而不是默认 Linux 行为。

---

## 六、一句话总结

方案的**产品边界、分期、记忆/对话/白标等决策**整体扎实，上游能力清单大部分核对无误；**唯一必须在下一次迭代前修正的是工作区**——把"自建 `capability-workspace` + `sessionBindings` + `/ext/workspaces`"改为"复用官方 `workspace.*` + `ctx.workspaces` + `session.create({workspaceId})`，自建侧仅补默认工作区种子与多用户预留字段"，并同步降级 R11、复用 `archiveSession`、把无人值守权限从"调研项"改为"已确认项"。这四处修正直接减少一期工作量、消除双事实源、并让 G2"升级适配成本最小化"真正成立（复用官方域 = 更少的自维护接缝）。
