## 0. 总体结论

方案的总体架构方向（插件化定制、上游零修改、slot 占用 root、锁版本 + adapter + 冒烟清单）**成立且纪律良好**，对上游机制的理解大部分准确（skill rank、system-prompt 接缝、存储三处 SQLite、React 18.3 等均通过源码验证）。

但存在一个**动摇方案根基的事实性遗漏**：上游 dsh 已经内置了完整的「工作区」域（持久化注册表 + 会话分组 + 归档 + RPC + 官方 UI 插件），方案却将其列为「上游没有的能力」并自建了 capability-workspace 插件与两张数据表。这直接推翻 F2 的实现机制、R11 风险定级、§10.4 待评审问题的前提，以及 P0 spike ④ 的必要性。**建议方案在进入 P0 前出 v0.5 修订**，把工作区数据层切换到上游原生域。

按严重程度：P0 问题 3 个（工作区重复建设、R11 前提失效、会话删除语义自建多余）、P1 问题 3 个（注入机制选型、ctx.storage 迁移风险被低估、共享 DSH_HOME 与卸载干净矛盾）、P2 建议若干。

## 1. P0 问题（影响方案根基，进入 P0 spike 前必须处理）

### P0-1 上游已内置完整 workspace 域，F2 属于大面积重复建设【最重要发现】

**事实（证据 E1/E2/E3/E4）**：上游 `@deepseek-ai/dsh-workspace` 随 web-app bundle 正式挂载发布，提供：

- `ctx.workspaceRegistry`：持久化工作区注册表——记录 = 稳定 id + canonical 目录路径 + 显示名 title + **会话分组 account** + 持久显示顺序（`packages/workspace/workspace/README.md`）
- 完整 RPC 域：`workspace.list / create / rename / delete / insertBefore / insertSessionBefore / archiveSession`（`packages/host/apiproxy/src/api/workspace.ts`）
- `session.create` RPC **直接接受 `workspaceId` 或 `cwd`**（二选一，schema 强制），传 workspaceId 时自动以工作区路径为会话 cwd 并 attach 进分组（`sessions.schema.ts:101-110`、`api-proxy.ts:2167-2228`）
- 官方客户端插件 `dsh-client-ui-workspace`（侧栏分组 UI）同样随 bundle 发布
- 启动时注册表自动用 `SessionPersistence.list()` 的 header cwd 把历史会话归组——「会话按工作区分组」的数据**上游自动维护**

**与方案的冲突**：

| 方案位置 | 方案主张 | 实际情况 |
|---|---|---|
| 01-background §2.2「没有的能力」 | "无「保存的项目目录列表 + 会话分组」持久层，需自建" | **不成立**，上游两者皆有且已发布 |
| 05-references §4.1 | RPC 域清单中自己列出了 `workspace.*` | 调研存档列出了该域，能力盘点却无视它——**文档内部自相矛盾** |
| 04-spec §4.1/§4.2 | 自建 workspaces 表 + sessionBindings 表 | 与上游 registry 记录、sessionIds account 完全同构 |
| 03-architecture §3 | capability-workspace 插件 | 存储层职责上游已承担 |
| 02-goals 功能清单 | 工作区是 9 项自研功能之一 | 可降级为「上游能力 + 薄 UI 层」 |

**建议（v0.5 修订方向）**：

1. 工作区元数据的**唯一事实源改为上游 registry**：`workspace.create(path)`（幂等，path 唯一由 canonical realpath 保证，正好覆盖方案 §4.1 的 path 唯一约束）；默认工作区 = 启动时对 `$DSH_HOME/workspaces/default/` 幂等调一次 create（上游 create 是 adopt-or-return 语义，天然幂等）。
2. 删除 §4.1 workspaces 表与 §4.2 sessionBindings 表；侧栏分组数据直接来自 `workspace.list`（返回 `sessionIds` 有序分组 + `archivedSessionIds`）。`title` 冗余缓存也不需要（sessionSummary 自带）。
3. 业务表对上游没有的业务字段（krm 的 scope、cronTasks 的 workspaceId、skillsMeta 的 workspaceId）**直接引用上游 WorkspaceId**，只把上游没有的预留字段（`status`/`ownerId`）放 /ext 补充表。
4. capability-workspace 插件撤销或瘦身为「默认工作区种子 + 业务字段补充表」；F2 自建量从「小」降为「极小」。
5. 副作用提示：上游 workspace 域同样是预发布契约，采纳后必须纳入 adapter 单点与升级冒烟清单（见 P2-3 的 R13 建议）。

### P0-2 R11（方案自评最高风险）的前提已被上游解决

方案 R11 称「`session.create` 是否接受 cwd/workspace 参数待验证」，并将其列为 F1/F2/F4/F5 的共同依赖、最高等级风险。

**事实（证据 E3）**：`session.create` 请求 schema 为 `{ workspaceId?, cwd?, sessionId?, agentPreset? }`，refine 规则「workspaceId 与 cwd 不可同传」；handler 中 `cwd = workspace?.path ?? request.payload.cwd ?? defaults.cwd`，随后 `workspace.attachSession(sessionId)` 自动归组。

**结论**：R11 可以直接关闭。P0 spike ④ 从「探索性验证」降级为「确认性验证」（跑一次 create-with-workspaceId 冒烟即可，建议并入既有 S6）。方案的 F1/F2/F4 的 cwd 绑定链路没有任何未知接缝。

### P0-3 §10.4 会话删除语义有官方通道，自建方案多余

方案 §10.4 称「上游 session RPC 面未见 delete」，因此自建「UI 隐藏 + /ext 记录」。

**事实（证据 E2/E4）**：`workspace.archiveSession` 就是官方通道——语义与方案设计**逐字吻合**：「从所有分组面隐藏、保留会话日志、保留工作区 account 槽位、可恢复（unarchive 恢复位置）、幂等」。上游 workspace 包 README 还明确记载了设计决策：「Session deletion and destructive folder removal are separate, absent capabilities; Workspace registration deletion never substitutes for either」——即上游有意只提供归档、不提供物理删除，合规角度与方案判断一致。

**建议**：删除语义改为直接调 `workspace.archiveSession`（archive 集随 `workspace.list` 返回，且有 changed 事件帧），撤销 /ext 侧的隐藏标记表。同样，F2 的工作区「软删除」语义也被上游 `workspace.delete`（只删注册、不动目录与日志）等价覆盖。

## 2. P1 问题（重要修正，影响 P3 设计与发布标准）

### P1-1 注入机制应优先 `ctx.systemPrompt.context()`，而非 section + 手写 session 事件

方案 D8/§6 设计：capability-krm 在 system-prompt 接缝贡献注入段，且「每次注入写一条 session 事件」以满足 C6「model-visible ⟺ logged」。

**事实（证据 E6）**：`dsh-system-prompt` 提供两类贡献接缝：

- `ctx.systemPrompt.section()`：静态段，拼接进 system prompt；
- `ctx.systemPrompt.context()`：**有序动态上下文**，README 明确「Providers are evaluated for each eligible assembly and **become a sourced runtime-context snapshot in model history** under the shipped loop」——即 context 内容**天然落会话历史**，C6 自动满足，无需手写事件（手写反而可能与上游快照双写、产生两份不一致的「事实」）。

此外还有 KV cache 维度的硬理由（证据 E6 README「KV Cache effect」节）：system prompt 任何变化会从第一个变化 token 起使全部会话的前缀缓存失效。方案的「记忆索引段」含新鲜度警告（按天变化）、「知识库摘要段」随条目启停变化——**放 section 意味着全量会话的 system 前缀缓存天天失效**；context 是 user-role 快照，不污染 system 前缀，是这类「每会话/每日可变内容」的正确位置。

**建议**：§6 重写为「krm 三段统一走 `ctx.systemPrompt.context()`，顺序由 context order 控制；落日志由上游快照机制承担」。P3 验收项 S4（注入可重建）改为验证模型历史中的 runtime-context 快照。遗留验证项：context 贡献的 scope（按会话绑定工作区过滤条目）如何拿到会话上下文——`AssembleContext` 支持 declaration merging 且 agent loop 已声明 `agent` 字段，可行性高，列入 P0/P3 确认项。

### P1-2 D4「ctx.storage 免自管 schema」的收益在预发布期不成立

方案 D4 选 `ctx.storage` 的核心理由是「官方抽象、随上游演进、免自管 schema」。但方案自己引用（且经核实，证据 E5）的上游事实是：**上游全部三处 SQLite「仅当前 SCHEMA_VERSION 可开、无迁移」**。

这意味着：上游升级若 bump storage schema 版本，用户机器上 `ctx.storage` 里的全部业务数据（工作区补充表、cron 三表、库索引、技能元数据、krm 三表）**直接不可打开**，与「自建 SQLite 遇到 schema 变更」的差别只是「断裂时由谁负责、以什么形式爆出来」。方案对此零着墨——升级冒烟清单（03 §7.3）没有任何一项覆盖「storage schema 变更后业务数据的处置」。

**建议**（不改 D4 结论，补风险管理）：

1. 升级冒烟清单新增 S8：「storage schema 版本变化演练」——旧版数据目录 + 新版二进制的启动行为有明确结论（拒绝启动？数据丢弃？），并提供业务数据导出/导入工具（/ext 加一个 dump/restore 端点即可，JSON 导出同时也是用户的数据可携带性特性）。
2. D4 决策理由改写：真实理由是「与上游一致性 + 代码量少 + 单用户量级 KV 足够」，而非「免 schema 管理」。
3. 维持方案已有的正确判断：libraryIndex / cronExecutions 两张增长表保留 `node:sqlite` 退路（§10.2 的回答：不必第一天自建，但退路写进 D4）。

### P1-3 多品牌默认共享 `~/.dsh` 与「卸载干净」「数据隔离」矛盾

方案 03 §9：多品牌共存开关**默认关闭（共享 `~/.dsh`）**。问题：

1. 共享模式下，BC Agent 的会话、设置、凭证、storages 与用户机器上的官方 dsh CLI / 其他品牌版**互相可见、互相污染**——与「数据不出本机」的产品承诺虽不直接冲突，但与品牌版之间的企业数据隔离预期冲突（同一源码出多个企业品牌版，企业 A 的会话出现在企业 B 的安装里不可接受）。
2. 成功标准 5「卸载干净」在共享模式下无法满足：卸载不能删 `~/.dsh`（会误删官方 dsh 或其他品牌版数据），则必然残留。
3. 凭证 4 级优先级中 `~/.dsh/.env` 一层同样被共享，品牌版间会互相继承 key。

**建议**：per-brand 独立 `DSH_HOME`（`%APPDATA%/<brand-id>/dsh-home`）**改为默认开启**，共享模式降级为显式 opt-in（面向确实想与官方 dsh 共享技能/会话的高级用户）；默认品牌（开源版）也应使用独立目录而非裸 `~/.dsh`。相应更新成功标准 5 的卸载语义。

## 3. 对评审请求的逐条回答

### 3.1（README 问题 1 / spec §10.1）记忆引擎：自建 vs TAM

**结论：自建正确，同意不引入 TAM。** 方案的论证（哲学不匹配、sidecar 打包/ABI/Node 版本成本、持续 token 消耗、beta 稳定性）充分，无需补充。

对「第三条路（借鉴 L1 dedup 增强自建版）是否纳入 P3」：**不建议纳入 P3**。手动管理的四类型记忆在单用户量级（几十到几百条）下，向量去重的边际价值接近零，反而引入 sqlite-vec 原生模块的打包负担（这正是否决 TAM 的理由之一）。正确时点是 P5 后的「自动沉淀」增强：届时写入通道是**模型面工具写同一张 memories 表**，与手动管理天然统一——dedup 需求若届时真实出现，再评估 TAM sidecar 或轻量向量方案。v0.8.1 §6 的手动体系本身不依赖去重（用户对自己写的记忆有全貌）。

### 3.2（README 问题 2 / spec §10.3）对话区嵌入官方 slot

**结论：策略正确，收益明显大于风险。** 自研对话区 = 重写约 20 个 ui-* 插件的工作量 + 直接耦合无版本 RPC 协议，方案 D2 的否决理由成立。

补充两条 P0 追加项（回应「是否需要在 P0 追加样式审查」——需要，且不够）：

1. **slot 内容清单**：禁用 ui-layout 后，20 个 ui-* 插件各自注册到哪个 slot（sidebar/conversation/details/shell.overlay，还是 root 的其他子位置）需要逐一列出。桌面参考项目的高级模式只验证了骨架可行；若 ui-jobs / ui-commands / ui-plan 等注册位置依赖 ui-layout 提供的中间层，禁用后可能**悄悄消失而不报错**——这是比样式冲突更隐蔽的风险。
2. **样式审查**：官方 conversation 组件树的 CSS 变量覆盖范围（`--dsw-*` 令牌清单）在 P0 列全，确认 manus 风格令牌能完整映射；映射不上的部分（组件硬编码色值）数量决定「嵌不入」风险的真实等级。

### 3.3（README 问题 3 / spec §10.2）业务存储：KV vs 自建 SQLite

**结论：KV 起步可以接受，但决策理由要改写（见 P1-2）。** 不建议第一天切 `node:sqlite`：单用户量级下 KV 全量扫描的瓶颈（方案自估万级）在库索引与执行记录两张表上最先到达，这两张表恰好是结构最稳定、最适合关系化的——保留「插件内开自有库」的退路（方案 D4 已写）即可，触发条件定为「库索引 > 5 千条或库页查询实测 > 200ms」。cronExecutions 另建议加**保留策略**（如每任务保留最近 200 条），从源头压住增长。

### 3.4（README 问题 4）上游适配策略是否足够

**方向正确，清单有缺口。** 锁版本 + adapter 单点 + 冒烟清单是预发布期唯一正确姿势。缺口：

1. 冒烟清单缺 storage schema 断裂演练（P1-2，建议 S8）；
2. adapter 单点目前只覆盖**前端**（`adapters/upstream.ts`）；Host 侧各 capability 插件直接消费 `ctx.*`（webServer/storage/sessions/workspaceRegistry/systemPrompt/timer），这些触点分散在 6 个包中，建议在 capability-core 内维护一份**Host 侧触点清单**（不必包一层 adapter——`ctx.*` 是文档化契约，包 adapter 收益低——但清单要进升级 PR 模板）；
3. 采纳上游 workspace 域后（P0-1），`workspace.*` RPC 与 `ctx.workspaceRegistry` 进入触点清单与 S2 冒烟；
4. 「上游 release note 盯梢点」建议加：`workspaceRegistry` 契约、system-prompt assemble waterfall 签名。

### 3.5（README 问题 5 / spec §10.7.3）完整性缺口

- **最大缺口即 P0-1**（上游 workspace 域未纳入）。
- **会话搜索入口缺失**：上游有 `session.search` RPC（限 500 字符查询、返回 snippet），方案 F1 只列了重命名/删除/切换/导出。侧栏会话增长后搜索是刚需，建议补入 F1（工作量极小）。
- `session.fork`（上游有）无产品入口——可接受，建议显式记录为「有意省略」而非遗漏。
- 库（F5）目录扫描的**排除规则未定义**：工作区目录扫描「含子目录」会把 `node_modules`、`.git`、构建产物一起索引。需补：遵循 `.gitignore` 或内置排除清单 + 单文件大小上限。
- cron 执行摘要「取最后一条 assistant 消息」需定义边界：会话以工具调用结束、被取消、或最后一条是审批拒绝时的取值规则。
- 技能「编辑使用范围 = 卸载重装」会重置安装记录——§4.6 以 name 为键可保留 useCount/lastUsedAt，但规格应显式写明「统计跨重装保留」，避免实现时按路径关联导致统计清零。

### 3.6（README 问题 6 / spec §10.5）多用户预留是否足够

`ownerId`/`status` 零成本字段策略**本身够用**（同意 §4.9 的判断标准：不产生 UI 复杂度或写入分支才预留）。但采纳上游 workspace 域后出现一个新的演进成本点，必须写进 G3：**多用户期工作区数据要从上游 registry（本地 KV）迁移到企业 PG 的 projects 表**，届时上游 WorkspaceId 与企业侧 id 的映射需要一张迁移表。这不改变单用户期的设计，但应在 G3 留一句话，避免多用户期才发现工作区数据锁在上游存储格式里（且上游格式无迁移承诺，见 P1-2——导出工具在此再次复用）。

### 4.3 文档内部一致性问题（v0.4 简化后的残留，修订时一并清理）
