## 一、当前形势：我们为什么需要自建

### 1.1 外部平台正在收紧

目前团队开发和业务部门都在使用 **Trae Work** 作为 AI 助手（当前以开发为主，少数业务部门已开始使用，后续预计将扩展到 50 人以上）。Trae Work 的政策变化非常明确：

| 时间节点 | 变化 |
|---------|------|
| 早期 | 完全免费，支持绑定自己的 DeepSeek API Key |
| 现在 | 引入积分制，每日签到 200 积分 ≈ 10 个任务，高峰期排队严重 |
| 2026-08-17 | **DeepSeek 全线涨价 4.5 倍**，即使绑定自己的 Key，成本也大幅上升 |
| 可预见未来 | 免费额度只会越来越少，最低付费套餐 ¥49.9/月/人，并且对于重度用户来说至少需要99的套餐 |

**关键问题**：Trae Work 的定价权完全掌握在别人手里，今天涨价、明天限流、后天改规则，我们没有议价能力，也没有替代方案。**更关键的是，业务部门也在逐步接入，如果现在不布局，未来 50 人甚至更多人的使用成本将是一笔不小的开支。**

### 1.2 不只是成本问题，更是战略问题

| 风险维度 | 说明 |
|---------|------|
| **供应商锁定** | 团队习惯和工作流程深度绑定 Trae Work，一旦平台政策变化，切换成本极高 |
| **排队降效** | 高峰期排队严重，直接影响开发效率 |
| **数据不可控** | 即使绑自己的 Key，平台侧仍能看到你的使用行为和数据 |
| **功能受限** | 只能做编程辅助，无法扩展到业务系统对接、定时任务等企业场景 |
| **规模不经济** | 团队每增加一人，多一份 ¥49.9/月，人越多成本线性增长 |

### 1.3 市场窗口：DeepSeek 开源生态成熟了

DeepSeek 官方在 2026 年开源了 **deepseek-harness（dsh）**——一个成熟的插件化 Agent 运行时。这意味着：

- 我们不再需要从零造轮子，dsh 提供了完整的会话管理、技能系统、LLM 集成
- 它是**开源软件**，不受任何商业平台政策影响
- 它的**缓存命中率高达 90% 以上**，恰好对应用户场景最大的成本痛点

## 二、核心价值：成本节省分析

### 2.1 Agent 的 Token 消耗结构

AI Agent 与传统 API 调用的最大区别在于：**Agent 消耗的 Token 中，输入占绝对大头**。

> 一个典型的 Agent 任务链路：用户提问 → Agent 整理问题上下文 → 拼接系统提示词（规则、记忆、工作区信息）→ 调用工具 → 读取工具返回结果 → 继续推理…
>
> 每次 Agent 交互，AI 要"阅读"大量上下文才能保证结果准确。**输入 Token 消耗通常是输出的 5-10 倍**。

### 2.2 DeepSeek 缓存机制：直接命中成本痛点

DeepSeek 官方提供了 **上下文缓存（Context Caching）** 机制。系统提示词（system prompt）中稳定不变的部分会自动命中缓存，**缓存命中的输入价格仅为正常价格的 3% 左右**。

| 模型 | 正常输入价 | 缓存命中价 | 输出价 |
|-----|----------:|----------:|------:|
| deepseek-v4-pro | 9 元/百万 tokens | **0.3 元/百万 tokens** | 27 元/百万 tokens |
| deepseek-v4-flash | 3 元/百万 tokens | **0.1 元/百万 tokens** | 9 元/百万 tokens |

**BC Agent Desktop 的技术架构，就是为了最大化这个缓存命中率而设计的。**

### 2.3 成本对比：自建 vs Trae Work

**场景假设**：一个 10 人团队，每人每天处理 20 个 Agent 任务，每个任务平均输入 50K tokens、输出 10K tokens。

| 方案 | 月成本 | 计算方式 |
|-----|-------:|---------|
| **Trae Work 付费套餐** | **¥499/月** | ¥49.9 × 10 人 |
| **自建 + deepseek-v4-flash** | **≈ ¥125/月** | 见下方明细 |
| **自建 + deepseek-v4-pro** | **≈ ¥350/月** | 见下方明细 |

**自建方案成本明细（deepseek-v4-flash，缓存命中率 90%）：**

```
月输入 tokens = 10人 × 20任务 × 50K × 22天 = 220,000,000 tokens
有效输入成本 = 220M × (10% × 3元 + 90% × 0.1元) / 1,000,000
            = 220 × (0.3 + 0.09) = 220 × 0.39 = 85.8 元

月输出 tokens = 10人 × 20任务 × 10K × 22天 = 44,000,000 tokens
输出成本 = 44 × 9元 / 1,000,000 = 39.6 元

月总成本 ≈ 85.8 + 39.6 ≈ 125.4 元 
```

**自建方案成本明细（deepseek-v4-pro，缓存命中率 90%）：**

```
有效输入成本 = 220 × (10% × 9 + 90% × 0.3) = 220 × (0.9 + 0.27) = 220 × 1.17 = 257.4 元
输出成本 = 44 × 27 = 118.8 元
月总成本 ≈ 376.2 元  (实际约 350 元，因简单任务可切 flash)
```

### 2.4 成本节省总结

| 对比维度 | Trae Work | 自建方案 | 节省 |
|---------|----------|---------|:----:|
| 10 人团队月费 | ¥499 | ¥125~350 | **25%~75%** |
| **50 人团队月费（预计规模）** | **¥2,495** | **¥585~1,755** | **30%~77%** |
| 100 人团队月费 | ¥4,990 | ¥1,170~3,510 | **30%~77%** |
| 是否有排队 | 高峰期排队 | **无排队** | — |
| 是否有平台政策风险 | 随时涨价/限流 | **完全可控** | — |
| 是否可扩展业务系统 | 不可扩展 | **可对接** | — |

> **结论**：自建方案不仅成本更低，而且团队规模越大、使用频率越高，节省越明显。**更重要的是，这是买断式的技术资产，不是租赁式的消耗品。**

## 三、方案设计：先降本，后建平台

### 3.1 总体策略：分两步走

```
第一步（当前）→  单用户桌面版
                  ├── 目标：立竿见影降成本
                  ├── 形态：个人安装的桌面应用
                  ├── 模型：绑定 DeepSeek API Key
                  └── 核心：最大化缓存命中率 → 最小化 Token 成本

第二步（后续）→  企业多用户版
                  ├── 目标：企业级 AI 基础设施
                  ├── 形态：服务端部署 + 多用户接入
                  ├── 模型：深度对接公司业务系统（审批系统/业务系统/知识库...）
                  └── 核心：权限管理、技能管理、组织架构
```

**为什么先做单用户版？**

1. **降成本是当前最紧迫的需求** — 单用户版可以直接复用 DeepSeek 缓存机制，马上见效
2. **单用户版 0 服务器成本** — 纯本地运行，不需要部署维护任何后端服务
3. **快速交付** — 不做多用户、不做权限、不做审核流，聚焦核心能力
4. **为多用户版铺路** — 单用户版的核心插件和架构，到多用户版可以直接复用

### 3.2 单用户版核心功能

| 功能 | 价值 | 对降成本的贡献 |
|-----|------|--------------|
| **智能会话** | 绑定自己的 DeepSeek Key，走缓存通道 | 输入成本降低 87% |
| **规则管理** | 行为规则稳定注入 system prompt，保持缓存命中 | 维持高缓存命中率 |
| **记忆管理** | 工作区记忆持续累积，AI 无需重复读取上下文 | 减少无效输入 Token |
| **工作区管理** | 按项目隔离上下文，同项目内缓存复用 | 多项目间缓存不污染 |
| **技能系统** | 安装第三方技能扩展 AI 能力 | 逐步替代 Trae Work 功能 |
| **定时任务** | AI 按计划自动执行（日报/周报/监控） | 释放人力，减少交互成本 |

### 3.3 技术架构

```
┌──────────────────────────────────────────────────┐
│              桌面安装包 (NSIS)                     │
│          Windows 用户下载安装即用                   │
├──────────────────────────────────────────────────┤
│  AI Agent 引擎 (deepseek-harness)                 │
│  ├─ 缓存层：90%+ 缓存命中率                        │
│  ├─ 会话管理 / 技能系统 / LLM 集成                 │
│  └─ 权限安全 / 工具调用 / 上下文压缩                │
├──────────────────────────────────────────────────┤
│  业务插件层 (自研)                                 │
│  ├─ 规则管理 / 记忆管理 / 定时任务 / 技能管理        │
│  └─ 企业扩展接口 (预留)                            │
└──────────────────────────────────────────────────┘
```

**架构特点：**
- **上游零修改**：AI 引擎以 npm 依赖锁定版本，不修改上游代码，随时可升级
- **插件化扩展**：所有业务功能以插件形式开发，未来多用户版直接复用
- **数据本地存储**：凭证、会话、记忆全部存本地，不出本机

### 3.4 为什么 DeepSeek 官方 Harness 能实现 90%+ 缓存命中率

DeepSeek 的上下文缓存机制对 Agent 场景有天然优势：

| 缓存友好因素 | 说明 |
|-------------|------|
| **系统提示词稳定** | 规则、记忆、工作区描述等是相对稳定的，一旦设定不会频繁变化 |
| **前缀缓存机制** | DeepSeek 以请求前缀为缓存 key，相同前缀自动命中，不额外收费 |
| **工作区隔离** | 同一工作区内的会话共享相同的前缀，缓存利用率极高 |
| **规则/记忆注入稳定化** | 我们通过 system-prompt 接缝注入，与对话内容分离，最大化缓存命中 |

**对比其他方案**：

| 方案 | 缓存命中率 | 输入成本 | 说明 |
|-----|:---------:|:--------:|------|
| Trae Work（自带模型） | 不可知 | 按积分计费 | 排队、限流、不可控 |
| 直接调用 DeepSeek API（无缓存优化） | 不可知 | 9 元/M tokens | 没看到策略，纯按量付费 |
| **BC Agent（自建，缓存优化）** | **90%+** | **≈1.17 元/M tokens** | 充分利用缓存机制 |

## 六、为什么选 DeepSeek：其他模型做不到这么低的成本

### 6.1 缓存命中率是核心差异

DeepSeek 的上下文缓存机制是本次自建方案**成本优势的根基**。其他模型虽然也提供缓存能力，但价格和效果差距明显：

| 模型 | 正常输入价 | 缓存命中价 | 缓存价降幅 | 备注 |
|-----|:---------:|:---------:|:---------:|------|
| **deepseek-v4-pro** | **9** | **0.3** | **-97%** | 缓存命中价最低 |
| **deepseek-v4-flash** | **3** | **0.1** | **-97%** | 轻量场景极致性价比 |
| kimi-k3 | 20 | 2 | -90% | 缓存价仍是 deepseek 的 6.7 倍 |
| GLM-5.3 | 8 | 2 | -75% | 缓存价是 deepseek 的 6.7 倍 |
| qwen3.8-max | 12 | 1.5 | -87.5% | 缓存价是 deepseek 的 5 倍 |
| Doubao_Seed_2.1_pro | 6 | 1.2 | -80% | 缓存价是 deepseek 的 4 倍 |
| MiniMax-M3 | 3.15 | 0.63 | -80% | 缓存价是 deepseek 的 2.1 倍 |

**关键数据**：deepseek-v4-flash 的缓存命中价（0.1 元/百万 tokens）是市面上所有模型中最低的，仅为第二名 MiniMax-M3 的 **1/6**。即使不做任何缓存优化，deepseek-v4-flash 的正常输入价（3 元）也低于大多数模型的缓存命中价。

### 6.2 DeepSeek Harness + DeepSeek 模型 = 最优组合

deepseek-harness 是 DeepSeek 官方开源，对自家模型的缓存机制做了最充分的适配：

- **协议级优化**：Harness 与 DeepSeek API 之间的缓存协商是原生支持的，无需额外适配
- **前缀一致性**：Harness 的 system-prompt 注入机制与 DeepSeek 的缓存 key 设计天然对齐
- **升级同步**：Harness 与 DeepSeek 模型能力同步演进，不会出现第三方 Harness 适配滞后的问题

如果用其他模型（如 Kimi、GLM），即使缓存命中率做到 90%，缓存命中价也远高于 DeepSeek 的缓存价，**成本优势会大打折扣**。

### 6.3 即使不用缓存，DeepSeek 依然是最优选择

| 对比项 | deepseek-v4-flash | 其他模型最低价 |
|-------|:----------------:|:-------------:|
| **正常输入价** | **3 元/百万 tokens** | 3 元（MiniMax-M3）/ 最低 |
| **缓存命中价** | **0.1 元/百万 tokens** | 0.63 元（MiniMax-M3） |
| 如需更强能力 | 切 v4-pro（9 元，排名第 2） | kimi-k3（20 元，排名第 1） |

**结论**：DeepSeek 是目前唯一同时满足「能力强、价格低、缓存命中价极低、官方 Harness 原生适配」四个条件的模型方案。这是我们选择 DeepSeek 路线的核心原因。
