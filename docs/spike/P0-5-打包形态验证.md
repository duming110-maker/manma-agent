# P0-5 spike：打包形态验证——client 插件构建产物在官方 loader 下运行

- 版本：v1（2026-08-18，P0-5 产出）
- 上游事实来源：`reference/upstream`（git SHA `99f6f02f`，npm `0.1.0-rc.7`，与 `upstream.json` 一致）。文中路径均相对 `reference/upstream/`，行号以该 SHA 为准（漂移时以文件内容为准）。
- 结论先行：**验收标准满足**。`@bc-agent/web-ui` 的构建产物 `lib/client.js`（esbuild 双产物的浏览器半）在官方 `window.__ModuleLoader__` 机制下被加载并执行：HTTP 产物与磁盘产物**字节级一致**（sha256 同值 + `cmp` 无差异）；roster 行的 `rev` 逐字符等于 `sha1(产物)[0:12]`；`graph.rev` 复算一致；用**官方 `ClientModuleSystem` 本体**（npm 安装份，非 reference）在 Node 沙盘里对 served 字节做注册/物化/require 边全断言 PASS。`build.mjs` 无契约违反——**本卡零代码改动**。

## 1. loader 机制（源码级出处）

### 1.1 模块表与全局壳 `window.__ModuleLoader__`

- **构造即安装 sink，每页一次**：`ClientModuleSystem` 构造函数（`packages/client/modules/src/client/system.ts` L77–96）先把 boot 行索引成 `graphRows`（重复 id 立即抛错，L82），随后在 `globalThis` 上安装 `window.__ModuleLoader__ = { load(handoff) }`（L86–95）。已存在即「double boot」抛错（L87）。这是内核的 bootstrap 例外：装载插件的机制本身不能经它自己到达（`modules/src/client/index.ts` 文件头注释）。
- **`.load` 的参数（注册 handoff 形状）**：`ClientPluginHandoff = { id, factory }`（`modules/src/client/manifest.ts` L146–156）。`id` 是注册键，**必须与被执行的 graph 行 id 一致**（同一 package name）；`factory: (require) => exports` 是闭包工厂，持全部 bundle 主体。重复注册同 id 抛错（system.ts L89–94，「bundle executed twice without invalidate」）。
- **惰性 CJS 模型**：脚本执行**只注册** factory，一切模块副作用（含 CSS 注入）都在 factory 闭包内、首次 import/require 时（物化）运行，物化结果 memoize 进 `loadCache`（system.ts L113–133；manifest.ts 文件头 L8–26 契约陈述）。
- **`require` 分支序**（factory 收到的同步 require，system.ts `makeRequire` L142–156）：shell 种子表（seed）→ shell 自有 statics → 已 memoize 记录 → 已注册 factory（递归物化，加载序自解）→ **其余一律抛错**（「missed the module table」——构建期 bundle 纯度门的运行时镜像）。`import()` 多一条 graph 行分支：先 `arrive()` 拉取脚本（system.ts L158–178）。
- **`arrive()` 的到达契约**：经 `loadBundle`（默认实现 = 同源 classic `<script src>` 元素，加载后即从 DOM 移除，system.ts L12–26）拉取 URL；脚本执行完必须已有该行 id 的注册，否则抛「loaded without registering "<id>"」（L104–107）。并发共享同一 in-flight 任务（L99–111）。
- **样式所有权**：物化结束时 `claimStyles` 把 factory 执行期间注入的**未打标** `<style>` 认领为 `data-plugin="<id>"` 并盘点进 `record.styles`（system.ts L41–51）——注意这只覆盖「factory 执行期间」注入的样式；**apply 时机**（cordis entry 激活后）注入的样式不在认领范围，须插件自理销毁（bc-web-ui 的 `mountShellStyles` 自带 disposer，符合）。
- **HMR/失效**：`invalidate(id)` 清 factory + record，下次 prefetch/import 重新拉取（L192–195；官方行为规格见 `modules/tests/loader.client.spec.ts` 「HMR reset」）。

### 1.2 rev / 缓存语义（host 半，`modules/src/index.ts`）

- **rev 的定义**：`shortHash = sha1(产物文件字节).hex.slice(0, 12)`（L144–147）；行激活时计算一次（`initialBundleRevision` L374–381，ENOENT 聚合成「client bundle not found; run pnpm run build」的启动错误）。
- **URL 形状**：`graphRow()` 拼出 `/plugins/<id>/client.js?rev=<rev>`（L150–158）；graph 级一致性锚 `rev = shortHash(JSON.stringify(entries))`（`compose()` L315–318）。
- **rev 的生命周期**：激活后**钉在行上**，fiber 重启不重算；**唯一**重哈希入口是 `rebuilt(id)`（HMR watch 的注册钩，L274–292）；「插件集合变化要重启才生效」（pkgMeta 缓存永不过期，L186–191 注释）。
- **服务路由**：`webServer.register({kind:'prefix', path:'/plugins'})`（L241–244）。`serveBundle`（L421–457）：仅 GET/HEAD（否则 405）；URL pathname 解码后按 `/plugins/<id>/client.js`（或 `.js.map`）查 `exports['./client']` 解析出的物理路径；未知资源 404；**200 响应固定 `content-type: text/javascript; charset=utf-8` + `cache-control: no-cache`**（L447–451）——缓存失效靠 `?rev=` 查询串（浏览器/中间层对 no-cache 资源按完整 URL 区分），不靠响应头。
- **boot manifest 注入**：`tapIndex` 把 `window.__DSH_BOOT__ = <json>` 作为 `<head>` 里第一个 `<script>` 注入（`injectBootManifest` L168–175；`<` 转义为 `\u003c` 防逃逸）——必须在 shell bundle 读它之前。

### 1.3 扫描面（谁进 roster）

- 解析锚点是 **profile 目录**（`ctx.baseUrl` = cordis.yml 所在目录）：`createRequire(ctx.baseUrl).resolve('<pkg>/package.json')`（L209–213）——**`exports['./package.json']` 是扫描器的硬性要求**（skin-plugin 踩坑记录；pnpm 隔离布局下从 modules 包自身 URL 解析会漏兄弟包，故锚定 profile）。
- `dsh.client` 声明逐字段校验（`parseDshClient` L109–129）：`platform` 必须字符串且激活判定要求 `=== 'web'`（L350）；`inject` 可选 string[]（**信息性**图元数据，manifest.ts L46–49：权威边在各包自身 cordis 声明里）；`immediately` 可选 bool（stage-one 预取层标记）。
- `exports['./client']` 取相对路径（字符串或一层 `{default: string}`，`clientExportOf` L131–142）；声明了 `dsh.client` 却无 `./client` 导出 → 启动即抛（L355–357）。
- 行资格：loader entries 里存在**启用且已建 fiber** 的同名行（`processOne` L384–401）。本次实测 roster 38 行、无 ui-layout 行；`immediately` 层 9 个全是基础设施包（typert-registry/api-gateway/hmr/modules/connection/remotes/runtime/ui-theme/locale），所有 ui-* 与 bc-web-ui 均为惰性层——**我们 `inject` 的 runtime 与 ui-theme 恰都在预取层，factory 在我们物化前必已注册**。

### 1.4 boot 消费链（`packages/client/web/src/boot.tsx` `AppWebEntry.run()`）

1. `parseBootManifest(window.__DSH_BOOT__)`（L98）——缺失/畸形直接 reject，整页无可引导对象。
2. `new ClientModuleSystem({modules: 行, staticModules: getStaticModules()})`（L100–102）——**sink 在此安装**；种子表见 `web/src/seed.ts` L29–41（`satisfies Record<PlatformModule, unknown>` 编译期钉死键集，与 `web/src/platform.ts` L8–15 的 10 个冻结词一字不差：`react`、`react/jsx-runtime`、`react-dom`、`react-dom/client`、`@deepseek-ai/cordis`、ui-slots、web-react、ui-primitives、ui-attachment、schema-form）。
3. `registerStatic(APP_SHELL_ID)` + `registerStatic(MODULES_ID, ModulesClient)`（L105、L111）——shell 自有模块与 modules 包自身的 client 半都**静态注册**（后者的 graph 行永不 fetch）；`window.__DSH_MODULES__ = 实例`（L112，内核交接槽，`./client` wrapper 的 apply 读它 provide `ctx.modules`）。
4. 渲染 loading 页（L114–127），**并行**启动 `immediately` 层预取（L133；`prefetchImmediateTier` L151–158——只注册 factory，单行失败静默、由 import 路径负责响亮上报）。
5. 挂 vendored cordis Loader 并在其存在任何 entry 之前注入 `loader.internal = modules`（L164–169——浏览器里 bare-import 回退是必然失败，只配当绊线）。
6. 预取 barrier 之后并发建 entries：`[MODULES_ID, ...roster 行, APP_SHELL_ID]`（L189 + L196–204）；非 immediately 行（含 bc-web-ui）在此步的 import 里才发生网络拉取与物化。
7. `loader.await()` + `assertEntriesActive` 全量清点（L206–207、L216–237）：任何 entry 无 fiber（import 失败）或非 ACTIVE（apply 抛错=FAILED、等不到服务=PENDING 并点名缺谁）→ 整页停在 loading 并逐条报错；全 ACTIVE 才 `settled.set(true)`，AppRoot 一次性切到 `appShell.renderApp()`（L137、L120–125）。

### 3.2 浏览器断言（PM 在真实浏览器 DevTools Console 执行复验）

```js
// B1 官方 sink 在场（boot 内核安装，每页一次）
typeof window.__ModuleLoader__ === 'object' && typeof window.__ModuleLoader__.load === 'function'
// → true

// B2 roster 行：存在、无 ui-layout、rev 与产物哈希一致（rev 值对照 §3.1 A2）
window.__DSH_BOOT__.entries.find(e => e.id === '@bc-agent/web-ui')
// → {id:'@bc-agent/web-ui', url:'/plugins/@bc-agent/web-ui/client.js?rev=37e50314b845',
//     rev:'37e50314b845', inject:[…2 项]}
!window.__DSH_BOOT__.entries.some(e => e.id.includes('ui-layout'))   // → true

// B3 模块表含我们的插件（内核交接槽 → loadCache 有行 = 已注册并物化）
window.__DSH_MODULES__.loadCache.has('@bc-agent/web-ui')   // → true

// B4 物化产物的形状（exports 面即对象插件面）
const rec = window.__DSH_MODULES__.loadCache.get('@bc-agent/web-ui')
typeof rec.exports.apply === 'function' && JSON.stringify(rec.exports.inject) === '["slots","theme"]'
// → true

// B5 require 边（react 未内联的运行时证明；种子身份在 shell 侧）
[...rec.edges]   // → ['react/jsx-runtime']

// B6 加载无错误（assertEntriesActive 全过 + 我们的 apply 已跑）
document.querySelector('style[data-bc-web-ui="shell"]') !== null   // → true（自管样式标签）
document.querySelector('.bc-web-ui-frame') !== null                // → true（boot 已 settle，侧栏在渲染）
```

注意：B6 第一条**不要**用 `style[data-plugin="@bc-agent/web-ui"]`——loader 的 `claimStyles` 只认领 factory 执行期注入的样式，bc-web-ui 的样式是 apply 期注入、自带 disposer（§1.1、C7），标签上只有自己的 `data-bc-web-ui`。`.bc-web-ui-frame` 仅在 boot settle 后存在（loading 页会被替换），因此它同时是「加载无错误」的可观察证据。

## 4. 构建形态结论

### 4.1 当前 esbuild 配置满足全部硬契约（C1–C8）

`packages/web-ui/build.mjs` 与 skin-plugin 的构建同构（两者的注册壳**逐字符一致**，均用 `const module`；`const`/`var` 差异是相对官方 tsdown intro（`tsdown.client.ts` 用 `var module = { exports: {} }`）而言——对 classic script 求值无语义差），且显式声明 `CLIENT_EXTERNALS`（react、react/jsx-runtime、runtime/client 豁免）。esbuild 的 `bundle:true + external` 与官方 tsdown 的 `external + noExternal(其余全内联)` 语义等价：**require 面即契约面**，本次实测 require 面 = `{react/jsx-runtime}` ⊂ 冻结表。**零代码改动**。

### 4.2 与官方 tsdown 预设 / skin-plugin 构建的差异（全部非违约）

| 差异点 | 官方 tsdown | bc esbuild | 评估 |
|---|---|---|---|
| sourcemap | `client.js.map` + `sourcesContent` + 路径镜像（L262–268） | 无（`.map` 404） | 排障体验缺口，P1 前补（§5） |
| `process.env.NODE_ENV` / `import.meta.env` 替换 | define 三键（L197–201，为内联的 node 惯用依赖） | 无 | 当前产物 0 处引用，安全；**准则**：日后内联任何探测 `process.env`/`import.meta.env` 的依赖（zustand 类）时必须先加等效 define，否则物化即 ReferenceError |
| external 清单 | 全量 `CLIENT_EXTERNALS`（10 词 + 豁免） | 子集 3 词 | 等价——esbuild 只为实际 import 的词发 require；全量表是上游 workspace 级预设的事 |
| CSS Modules | lightningcss 内联 + `data-plugin` 标签 | `styles.ts` 手写样式 + 自管 disposer | 契约兼容（C7 两分支都合法）；P2 换肤管线再评估 |
| roster 行来源 | 官方包随 web-app bundle 层 | bc 行经 `--patch` 叠加（apps/desktop） | 见 §4.3 第二决策点 |

### 4.3 P1 Electron 打包：插件产物随包分发的建议（不定案，供 PM 决策）

- **机制事实**：`dsh plugin --profile web add <spec>` 是 pnpm 转发器（`apps/cli/src/plugin.ts` L120–158；相对路径 spec 重锚到调用目录 L104–112），接受 `link:`（活链，dev 现状）、`file:`/裸目录（拷贝）、tarball、git/registry spec；安装后按「是否声明 `dsh.bundle`」对账 layer 栈（reconcilePlugins L59–91）。
- **建议（倾向）**：**发行形态 = 构建 tarball + 首启 `file:` 安装**——把 `packages/web-ui`、`capability-core` 等的构建产物打成 `@bc-agent/web-ui-<ver>.tgz` 随 Electron 资源分发，首启时 `dsh plugin --profile web add <资源内绝对路径>.tgz`（离线、不可变拷贝、免 registry；`apps/desktop/src/main.mjs` 的 `ensurePluginInProfile` 只需把 `link:` 换成 tarball 路径，幂等标记逻辑不变）。`link:` 保留为 dev-only（改码 rebuild 即生效的现优势）。**备选**：预装 profile 目录整体拷贝（耦合 DSH_HOME 布局与升级路径，不建议）；`file:` 活目录（发行机上目录可变，不建议）。
- **第二决策点（roster 行的官方通道）**：现走 `--patch` 叠加（组合权在应用层）；官方另一通道是插件自带 `dsh.bundle.patch`（skin-plugin 模式：安装即自动入 layer，reconcilePlugins L63–69）。发行版若想让插件包「装上即生效」而不依赖外部 patch 文件，可给 web-ui 补 `dsh.bundle.patch`（会顺带消掉安装时的「declares no dsh.bundle」告警，L70–74）；但这把组装权从应用挪进包里，与「profile 叠加」的架构叙述有张力——**留给 P1 定案**。

## 5. 已知缺口 / 需要 PM 确认的点

1. **sourcemap 缺失**（A5 的 404）：浏览器侧报错堆栈将落在压缩混合文本上。建议 P1 前给 build.mjs 加 `sourcemap` 输出并对齐官方 `sourcesContent` 形状（`/plugins/<pkg>/client.js.map` 路由已就绪，产出即被服务）。

3. **分发形态**（§4.3）：tarball-first-run vs 预装 profile、以及是否给 web-ui 补 `dsh.bundle.patch`——两个决策点请 PM 定夺后再进 P1。
