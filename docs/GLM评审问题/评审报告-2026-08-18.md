# BC Agent Desktop 方案评审报告

- 评审对象：`docs/bc_agent/` v0.4-draft（2026-08-17）全部六份文档
- 评审日期：2026-08-18
- 评审方法：通读方案文档，并对照上游 dsh 源码（当前 master 47f9438）逐项核查文档中的源码级主张。逐条核查结果与证据（文件:行号）见同目录 [事实核查-2026-08-18.md](事实核查-2026-08-18.md)。
- 问题编号规则：A（重大，动摇架构前提）、B（高，开工前应修订设计）、C（中，规格缺口或事实偏差）、D（低/建议）。

## 一、总体结论

方案整体质量高：三层架构、插件化集成路线（slot 占位 + 官方对话区嵌入）、升级适配纪律（锁版本 + adapter 单点 + 冒烟清单）与上游现实匹配；技能目录模型、slot 系统、webserver 接缝、Electron 打包参考等关键机制的选择都有源码级依据，核查绝大多数属实。

但对照源码发现 **3 个重大事实问题，直接影响 F2（工作区）、F4（定时任务）、F6/F7/F8（注入落日志）的设计前提**，建议开工前修订文档：

1. **上游已有完整的工作区注册表**（`@deepseek-ai/dsh-workspace` + `workspace.*` RPC + `session.create({workspaceId}|{cwd})`），F2「持久层需自建」的前提不成立（A1；同时 R11 可直接关闭）。
2. **「注入内容写 session 事件」当前不可行也不必要**：第三方自定义会话事件读取端默认拒绝；而官方 `request/header` 事件已把完整渲染后的 system prompt 落盘，C6 由官方接缝天然满足（A2）。
3. **`cordis-plugin-timer` 不支持 cron 表达式与时区**，D6 的调度机制描述不成立（A3）。

此外 §10.6（无人值守权限接缝）可直接给出答案，P4 前置调研项可关闭（A4）。

## 二、重大问题（A：动摇架构前提，开工前须修订）

### A1 上游已有工作区注册表，F2 与其大面积重叠；01 §2.2「需自建」结论错误

事实（均已源码核实）：

- `@deepseek-ai/dsh-workspace`（`packages/workspace/workspace/`）提供 `ctx.workspaceRegistry`：durable 工作区记录（canonical path 唯一）、稳定排序、会话账号（`sessionIds`，按会话 header cwd 校验挂接）、全局归档集（隐藏但保留日志与位次，可恢复）。web-app bundle 已默认挂载（`packages/bundle/web-app/cordis.patch.yml:73-74`）。
- `workspace.*` RPC 共 7 个方法（`packages/host/apiproxy/src/api/workspace.ts:38-109`）：`list` / `create`（幂等，目录必须已存在，不 mkdir）/ `rename` / `delete`（仅移除注册，不删目录与日志）/ `insertBefore` / `insertSessionBefore` / `archiveSession`。
- `session.create` 原生接受 `workspaceId` 或 `cwd`（二选一，schema 层互斥校验）：`packages/host/apiproxy/src/api/sessions.ts:261-262`、`sessions.schema.ts:102-110`；handler 内 `cwd = workspace?.path ?? request.payload.cwd ?? defaults.cwd`（`api-proxy.ts:2180`）。

影响：

- 01 §2.2「没有的能力」表中「工作区……无『保存的项目目录列表 + 会话分组』持久层，需自建」不成立。且 05 §4.1 的 RPC 域清单里其实已列出 `workspace.*`，与 01 §2.2 自相矛盾——调研存档与设计结论脱节。
- F2 的 workspaces 表（04 §4.1）、sessionBindings 表（§4.2）、`/ext/workspaces` 与 bindings API（§5）与上游注册表几乎一一对应：path 唯一约束、创建时绑定不可逆、目录永不删、侧栏分组、归档语义全部有原生等价物。自建平行账本会带来双写一致性与口径分裂（官方 session 列表/归档集 vs bc 绑定表）两类长期成本，也违背 G2「最小自建」。

建议：

- F2 改为「上游 workspaceRegistry 为唯一事实源 + bc 薄层」：侧栏分组直接消费 `workspace.list`（含 `sessionIds` 与 `archivedSessionIds`）+ 官方 session 列表；会话删除改用 `workspace.archiveSession`（同时回答 §10.4）；bc 仅保留：默认工作区种子逻辑、按上游 `WorkspaceId` 挂接的业务薄表（isDefault 等元数据）、cronTasks 的 workspaceId 引用。
- D7、数据模型 §4.1/§4.2、API 面 §5 相应缩减；`/ext/bindings` 反向查询可由 `workspace.list` 的 `sessionIds` 替代。
- **R11 就此关闭**：`session.create` 原生支持 cwd/workspaceId。P0 spike ④ 改为「基于 upstream workspace 跑通 `create({workspaceId})` → 该目录 `.agents/skills` 技能出现在会话中」。
- 保留提醒：workspaceRegistry 自身也是预发布（无兼容承诺），但消费官方面比平行自建的上游触点更小，方向上是降低而非升高 R1 风险。

### A2 「每次注入写一条 session 事件」不可行且不必要；C6 应由官方 `request/header` 落日志满足

事实：

- 读取端：未知事件类型默认**拒绝重建**会话，除非信封带 `ignorable: true`（`packages/core/session/src/types.ts:404-436`；`packages/session/session-persistence/src/coordinator.ts:1063-1064`）。事件词汇表头注释明确「out-of-repo 插件事件不在表内，注册面 deferred until such a consumer exists」（`packages/core/session/src/known-event-types.ts:12-17`）。
- 写入端：live 路径 `Session.append` 构造的信封不暴露 `ignorable` 参数（`packages/core/session/src/index.ts:604-633`），上游生产代码无任何写 `ignorable` 的先例。唯一能带 `ignorable` 的是持久化层原始接口 `ctx.sessionPersistence.append`（仅 contract 测试在用），它绕过事件 firehose 与投影，是内部逃生门而非第三方支持面。
- 同时，官方已把**每次组装后完整渲染的 system prompt** 写入 `request/header` 事件的 `header.system` 字段（`packages/core/session/src/types.ts:196-210、304`；写入点 `packages/core/agent-loop/src/agent.ts:337、458-469`，reason: initial/resume/change 快照）。capability-krm 经 `ctx.systemPrompt.section()`（`packages/core/system-prompt/src/index.ts:381-455`）贡献的段落天然包含在内。

结论：04 §6 第 3 条「每次注入写一条 session 事件」应删除；C6（model-visible ⟺ logged）由 D8 已选的官方 system-prompt 接缝自动满足。S4 冒烟改为「`request/header` 快照中可重建知识/规则/记忆三段」。若未来确需业务事件进会话日志，正确路径是推动上游开放第三方事件注册面，不要走 `sessionPersistence.append`。

### A3 `cordis-plugin-timer` 不支持 cron：D6 的调度机制描述不成立

事实：vendored timer 插件 API 仅 `ctx.timeout/interval/throttle/debounce`，全部是毫秒 delay 包装（`vendor/timer/README.md:24-36`、`vendor/timer/src/index.ts:12-15`），全文无 cron、无 timezone。base 挂载属实（`packages/bundle/base/cordis.patch.yml:15-17`）。

影响与建议：「按 cron 表达式驱动」需自建 cron 表达式解析 + 下次触发计算 + 时区处理（建议引入 cron-parser 类成熟库），timer 只作底层 interval/timeout 载体。04 §3.4「最小粒度 5 分钟，与上游 schedule 包最小间隔对齐」的类比应删除——本方案不使用 schedule（schedule 是 session 级提醒工具、不支持 cron、不在默认 web 组合中，仅 `examples/web-schedule` overlay 开启）。`timezone` 字段（默认 Asia/Shanghai）能否兑现取决于所选 cron 库的时区能力，需在 P4 实现时明确并进冒烟。

### A4 §10.6 无人值守权限接缝：已有明确答案，P4 前置调研项可关闭

事实：

- permission-presets 服务捆绑 `sandbox/mode` + `approval/policy` 两个旋钮，出厂预设 `workspace-write`(+ask) 与 `danger-full-access`(+never)（`packages/interaction/permission-presets/README.md`）；预设与会话创建时 pin，之后改全局设置不影响既有会话；`set(session, name)` 可按会话切换。
- `ApprovalPolicy` 仅 `'ask' | 'never'`；`'never'` = 不询问任何人、所有审批请求自动 resolve 为 `'rejected'`（fail-closed，`packages/interaction/user-approval/src/index.ts:90-97、181`）。
- web 组合默认经 `DSH_PERMISSION_MODE` 环境变量接线（`packages/bundle/web-app/cordis.patch.yml:168-191`）。

建议：cron 执行会话显式设为 `workspace-write`（或更保守 read-only）+ approval policy `never`：沙箱内自主执行、越权请求自动拒绝并可写进执行记录——与 04 §3.4 的保守默认语义完全对齐。注意默认预设表里存在 `danger-full-access`(+never)，cron 默认配置必须避开它。此项从「P4 前置调研」转为「P4 实现项」，结论回填 03 §6.5。

## 三、高优先级问题（B：开工前应修订设计）

### B1 D3 的事实依据不成立；`/ext` 走裸 `webserver.register` 不继承任何官方栅栏

- 「官方 RpcMethodMap 构建期固定，第三方扩不进去」只对点分方法表成立。`ctx.connection.rpc` 提供两个运行时扩展点（`packages/client/connection/src/rpc.ts:25-53`）：`intercept('/api', ...)`（`/api` 通道的拦截器座位已被 Typert 网关占用——`typert-gateway` 在 base 挂载，`packages/bundle/base/cordis.patch.yml:36-37`，且每通道仅一个拦截器）与 `handle(channel, ...)` 注册全新通道（自动挂上与 `/api` 相同的信任栅栏与 POST 强制 JSON，`rpc-host.ts:90-115、144-165`）。
- 官方栅栏的真实检查项：Host 头 loopback/trustedHosts + `sec-fetch-site: cross-site` 拒绝 + Origin 出现时必须与 Host 权限一致（`packages/client/connection/src/api-request-trust.ts:96-123`）。作用域为 `/api` 前缀与其 WS 升级路由；`webserver.register()` 是裸路由分发，"Knows no harness concepts"（`packages/host/webserver/src/index.ts:94-101`）。
- 后果：04 §6.3「/ext 只接受 loopback（capability-core 统一校验）」意味着自研并持续跟上上游栅栏语义，等于复制安全代码。建议 P0 spike 新增验证项：**用 `connection.rpc.handle('/ext', ...)` 承载业务 RPC**——继承官方栅栏、获得统一信封，同时回答 10.7.1（优于「全走自建 WS」与「裸 HTTP 自校验」两个备选）。若最终仍走 `webserver.register`，§6.3 必须列明要复刻的三项检查（Host / Sec-Fetch-Site / Origin）并加对应冒烟。

### B2 存储事实偏差影响 D4/10.2 判断：KV 并非 document-per-key，json 后端是「每域单文件全量重写」

- `ctx.storage.domain` API：`open/get` + KvTable 的 `get/put/delete/update/entries/keys/size`（`packages/storage/storage-domain/src/domain.ts:42-90`）；`entries/keys` 是内存全表快照迭代，**无前缀枚举**。
- json 后端（web 组合默认，`packages/bundle/web-app/cordis.patch.yml:51-62`）是**每 domain 一个 JSON 文件、整域序列化重写**（`packages/storage/storage-json/src/format.ts:24-35`）。「document-per-key」仅 sqlite 后端成立（document-per-row；`STORAGE_SQLITE_SCHEMA_VERSION = 1`，他版本拒开、无迁移）。04 §4 开头「document-per-key」表述需修正。
- 判断：workspaces/知识/规则/记忆/技能元数据在单用户量级下 KV 足够；但 `cronExecutions`（只增不减）与 `libraryIndex`（递归扫描产物）放 json 域意味着每次写入全文件重写、每次打开全量加载。建议 10.2 的答复直接落地为分层：**低量实体用 `ctx.storage`，执行记录与库索引第一天就进插件自有 `node:sqlite` 库**（把 D4 已保留的升级路径对这两个实体前移），并补数据保留策略（执行记录条数上限/清理、库索引重建按钮已有）。

### B3 会话日志升级断裂是独立产品风险，R1 未覆盖

- `SESSION_FORMAT_VERSION = 0`、无兼容承诺（`packages/core/session/src/types.ts:34-56`）；新版拒绝旧日志且「older: no upgrade path ships yet」（`packages/session/README.md:143`、`docs/subsystems/persistence.md:94`）。
- R1 只写了「API 破坏性变更」，没写**「用户升级 App 后全部历史会话不可读」**这一桌面产品不可接受的后果。缓解建议：发布标准 4「升级演练」增加「旧版本产生的会话日志在新版本可读」回归项；预案权 jsonl 文本迁移器（默认后端 jsonl 是纯文本，格式断裂时可在安装期转换）；风险清单单列一条（见第七节 R13）。

### B4 库的目录扫描缺忽略规则与上限

04 §3.5「直接扫描目录（含子目录）」：工作区是真实项目目录，`node_modules/.git/dist/target` 会造成上万条目与超时。需要：可配置忽略目录清单、深度/单目录文件数/总条目上限、二进制跳过（可复用扩展名+MIME 映射）、扫描放后台执行（可考虑上游 jobs 语义）。应作为新风险项（R15）。

### B5 知识库正文「落入工作区可读目录」会污染用户项目目录

工作区目录是用户真实项目（可能是 git 仓库），把知识条目正文写成文件落进去是未声明的仓库变更。两个候选各有约束：`<工作区>/.dsh/krm/`（在 cwd 内、文件工具确定可读，但污染 repo，至少需 .gitignore 引导）或 `$DSH_HOME/krm/<workspaceId>/`（不污染，但需验证会话文件工具对 cwd 外路径的读取策略——fs policy 接缝需 P3 spike）。§3.6 应明确选择并补验证项，而非现在的一句「落入工作区可读目录」。

### B6 `session.create` 不含 modelId：新建流程与 cron 链路需补时序

session.create 无 modelId/title（模型来自 Host 默认 `ctx.agentDefaultModel`，创建后经 `session.selectModel` 切换，`packages/host/apiproxy/src/index.ts:98-100`）。04 §3.1「选模型 → 发送」与 §3.4 cron 的 `modelName` 都需要 **create → selectModel → prompt** 的显式时序；§3.4 触发链路描述应更新。

### B7 `/ext` 域缺前端更新通道

业务态变更（cron 执行完成、技能统计、工作区变更）如何到达前端未设计：官方 `/api/events.*` 只转发上游事件，不会带 bc 业务态。至少明确策略：轮询 `/ext/app/bootstrap`（间隔多少）或 `registerUpgrade` 自建 `/ext` WS（广播变更信号）。缺推送通道时「执行记录 tab」会退化为手动刷新，与移植已完成 UI 的预期不符。

## 四、中优先级问题（C）

### C1 「已安装」技能清单与 `skill.list` 口径不一致

- 上游发现根共 7 层：文档列了 4 层（100/200/400/500），还有 runtime(250)/custom(300)/bundled(600)（`packages/skill/skill/src/index.ts:23-27`、`skill-filesystem/src/index.ts:241-261`）。capability-skillx 只自扫 4 层会漏官方运行时/内置技能——「已安装」页看不到、会话里却能用。建议已安装页增加「环境内置（不可管理）」分区或明确标注口径。
- `skills-disabled/` 移动停用机制核验**可行**（上游每根仅扫一层，子目录不发现，`skill-filesystem/src/index.ts:719-747`），但只对自管根有效；对 git 仓库内的工作区，移动 `.agents/skills` 下目录是在改用户仓库，UI 应提示。
- 对照：上游已有 frontmatter 调用策略 `disable-model-invocation`/`user-invocable: false`（`skill-filesystem/src/index.ts:992-1008`），语义是「隐藏调用面」而非「停用」，不建议与移动目录混用两套语义。

### C2 `/name` 手势是全文词边界匹配，不只是前缀

上游正则 `(^|\s)\/([a-z0-9-]+)(?=\s|$)` 扫描用户消息全部 text block，任意位置的 `/word` 命中技能名即触发（`packages/skill/tool-skill/src/index.ts:409-431`）。前端「粘贴不触发」只约束 Chip 下拉交互；用户粘贴含 `/xxx` 的文本发送仍会被当作技能调用。建议 §3.3 记录该语义，UI 可在发送前检测正文中的手势 token 并提示。

### C3 cron 并发与执行完成判定未定义

同一任务上一轮未结束下一轮到点（跳过/排队/并行）？多任务同时到点是否串行？「执行至完成」靠什么 API 判定？执行中取消如何与 `session.cancel` 协作？§3.4 与 §4.4 均未覆盖。建议补 overlap 策略（推荐：同任务 running 时跳过并记 skipped——执行记录状态机相应加 `skipped` 态）与并发上限。

### C4 技能市场 tab 数据源未定义

「社区/开源技能目录展示」的目录数据从哪来？上游社区市场未落地（02 已知事实），市场 tab 不能做成对不存在服务的隐性依赖。建议 P3 首版 = 内置静态推荐清单 + URL/zip/目录安装入口，§3.3 写明。

### C5 Windows 发行具体风险应点名进 R3/R4 缓解

- PowerShell 解析链：PS7 安装位置 → PATH → **Windows PowerShell 5.1 兜底** → 裸 pwsh（`packages/shell/pwsh-local/src/resolve.ts:21-37`）。仅 5.1 环境下非 ASCII stdin 可能误解码（`pwsh-local/README.md:55`）——中文产品高频场景，建议安装包检测并引导安装 PowerShell 7。
- Windows 沙箱是 ACL 受限令牌，保证级别 partial（Everyone 写边界、NTFS 硬链接逃逸等，`packages/sandbox/sandbox-windows-acl/README.md:45-81`）。cron 无人值守 + workspace-write 的威胁模型应引用该边界（呼应 A4）。
- Electron 特有坑上游已记录（`.agents/notes/implemented/architecture/2026-08-15-windows-electron-acl-runner.md`：`process.execPath` 需 `ELECTRON_RUN_AS_NODE` trampoline、控制台窗口闪烁）；demo 已有解法（`npmRebuild=false` + node-pty prebuilds + `asar.unpacked`）。注意：node-pty 的 asar 适配是**上游 workspace 的 pnpm patch**（`pnpm-workspace.yaml:72`），bc 独立 repo 必须自带同等 `patchedDependencies` 配置——R3 缓解清单应列全。
- 好消息也应记录：上游 CI 有原生 Windows 完整门禁（`windows-native` job），10.7.4 的答案是「没有被低估，且有 CI 背书」，但上述三点需进风险清单。

### C6 patch 语义修正：`insert` 无位置式插入

`insert:` 只能 append 到列表尾或推入某 group 行的 config（`vendor/include/src/index.ts:58-128`）；「在 web-app 层之后插入」靠 bundle 层序保证而非 insert 定位语法。03 §4 示意注释应改准确。另：bc patch 只需 disable `ui-layout` 一行，官方 `ui-sidebar`/`ui-conversation` 等行保持启用（demo advanced 模式的做法；patch 层 `disabled: true` 是官方用法，web-app patch 自身大量使用）。

### C7 数据模型小问题

- skillsMeta 的 `status` 枚举（enabled|disabled）与 §4.6 删除策略「元数据保留 deleted 态」不一致，需加第三态或独立字段。
- sessionBindings 若按 A1 简化则整表可删；若保留，title 冗余缓存与官方 `session/title` 事件（用户改名后 pin）的同步逻辑需写明。
- cronExecutions 状态机缺 `skipped`（C3 的错过/重叠语义）与超时态。

### C8 默认工作区种子与上游 `workspace.create` 的交互

上游 create 要求目录已存在（不 mkdir，`workspace.ts:50-57`）；种子逻辑需「先 mkdir `$DSH_HOME/workspaces/default` 再注册」。上游无 default workspace 概念，`isDefault` 放 bc 薄表（呼应 A1）。

## 五、低优先级与建议（D）

- **D1 备份/恢复/迁移未设计**：桌面产品必答题——DSH_HOME + 工作区元数据 + 库索引的导出/导入；卸载时数据保留策略（NSIS 选项）。建议进 02 目标或 04 §8 P5。

- **D3 品牌字面量 lint**：自研 ESLint 规则成本偏高，grep 脚本进 S7 即可满足发布标准 6。
- **D4 P0 spike 修订**：④ 改为基于 upstream workspace 的 `create({workspaceId})` 验证（A1）；新增 `connection.rpc.handle` 通道评估（B1）；新增官方 conversation 组件树样式审查（10.3 答复：同意追加）。
- **D5 主题盯梢**：`--dsw-alias-*` 变量名列入 §7.4 升级盯梢点（变量重命名会让换肤层静默失效）。
- **D6 10.1 答复**：同意自建，TAM 否决论证成立（哲学不匹配 + 打包/运行成本 + beta）。第三条路：P3 后可借鉴 L1 dedup 思想做低成本查重（标题/正文归一化 + 编辑距离阈值），不引向量。
